### 2. Trace 数据持久化修复

**问题**：`result_state["_trace"]` 在 `_execute_task()` 中赋值后从未写入数据库，`build_task_payload()` 也不返回 trace 字段。

**修复**（`backend/app/services/task_runner.py`）：

1. **持久化 trace**：在 `_execute_task()` 的 per-document 循环中，`set_execution_meta()` 之后、`db.commit()` 之前，将 trace 写入 `task.config["_trace"]`
   - 初始化 `all_traces: list[dict]` 收集每个文档的 trace
   - 单文档存为 dict，多文档存为 list
2. **API 返回 trace**：在 `build_task_payload()` 返回 dict 中添加 `"trace": (task.config or {}).get("_trace")`
3. 测试结果：276 passed，11 个 trace 专项测试全部通过

### 3. LLM Provider 显示修复

**问题**：Settings 页面只显示有 API key 的 provider（仅 SiliconFlow），应显示全部 8 个。

**根因**：`LLMEngine.get_available_providers()` 遍历 `self.adapters`（仅有 API key 的 adapter），而非 `PROVIDER_REGISTRY`（全部 8 个）。

**修复**（`backend/app/services/llm_engine.py`）：
- `get_available_providers()` 改为遍历 `PROVIDER_REGISTRY`
- 有 adapter 的 provider：`available=True` + adapter model
- 无 adapter 的 provider：`available=False` + registry default_model
- 更新测试：断言从 `len == 1` 改为 `len == 8`

## 五、潜在风险

### 高风险
1. **SiliconFlow API 稳定性**：LLM 调用耗时 ~4.5 分钟，依赖外部 API 可用性。如果 API 限流或不可用，审计管道会失败。
2. **Trace 数据大小**：`task.config["_trace"]` 存储在 SQLite JSON 列中，多次运行后数据库文件会膨胀。当前单次 trace ~5-10KB，100 次运行约 1MB，暂可接受。
3. **Exe 未包含最新修复**：当前打包的 exe 不含 trace 持久化、LLM provider 修复、AlertsPage 响应式。需要重新打包。

### 中风险
4. **Embedding 模型加载**：模型 1.3GB，启动时预加载耗时 ~10s。如果模型文件损坏或路径错误，KG 功能不可用。
5. **LightRAG 索引兼容性**：打包时复制的索引可能与目标机器的 Python/库版本不兼容，导致查询失败。
6. **tkinter 启动器同步**：启动器硬编码 8 个 provider，如果 `providers.py` 添加新 provider，需同步更新启动器。

### 低风险
7. **前端路由**：SPA 路由在直接访问 `/documents` 等路径时返回 404（需要从 `/` 进入后客户端路由）。这是 CRA 的已知行为，不影响正常使用。
8. **测试覆盖率**：41% 覆盖率偏低，关键路径（task_runner、llm_engine）测试覆盖不足。
